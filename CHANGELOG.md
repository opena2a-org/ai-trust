# Changelog

## Unreleased

### Security

- **`--registry-url` with `user:password@` in it is refused before any request, and its value is not echoed ([#232](https://github.com/opena2a-org/ai-trust/issues/232)).** `check x --no-scan` with such a URL printed `Error: Registry network error: Request cannot be constructed from a URL that includes credentials:` followed by the request URL, password included, and with `--json` put the same text in `error`. `check`, `audit` and `batch` now end before any request with `Error: --registry-url must not include credentials (user:password@). ai-trust sends no credentials to the registry; pass the URL without them. Example: --registry-url https://api.oa2a.org` and exit 1; with `--json`, `check` prints that text as `{"error": ...}` on stdout. A URL with only a user name or only a password is refused the same way. A `--registry-url` value that does not parse, which the existing error quotes, is quoted without the user name, password and `@` after its `//` (a value with port `99999` and credentials is quoted as `http://127.0.0.1:99999`).
- **A key that a scanner finding quotes from the scanned files is masked in text and `--json` output ([#217](https://github.com/opena2a-org/ai-trust/issues/217)).** The pinned `hackmyagent` 0.33.2 puts the matched text of its `AST-CRED-001` "Credential Harvesting Pattern" finding in the finding's message, a key in that text included, while its `AST-CRED-003` finding prints the key it reports masked. On a test agent with `sk-` keys in its `system-prompts.json`, `check <name> --scan-path <dir> --all` printed a 46-character key in full in the `AST-CRED-001` message, in the text output and in `--json`. ai-trust now masks credential-shaped values in each finding message when it reads the scanner's report. A value is masked when it starts with one of the scanner's vendor prefixes (`sk-ant-api` and a digit, `sk-proj-`, `sk-`, `sk_live_`, `sk_test_`, `ghp_`, `gho_`, `ghs_`, `ghu_`, `github_pat_`, `hf_`, `glpat-`, `npm_`, `AKIA`, `AIza`, `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-`, `xoxs-`, `SG.`) followed by the body the scanner requires after that prefix, or when it has the shape of a JWT: three or more dot-separated base64url segments, the first starting with `eyJ` and no letter, digit, `_` or `-` right before it. A prefix right after a letter or digit, as the `sk-` in `task-`, is not one. A masked value is printed as its prefix and one `*` for each further character, at most 16, the form in which `AST-CRED-003` prints a key. The same run now prints that key as `sk-****************`, and the score, the verdict and every other finding are as before. A value that starts with none of these prefixes and does not have the shape of a JWT is printed as the scanner wrote it. The scanner's own report still carries the key; that needs the same fix in `hackmyagent`.
- The bundled scanner runs without `ANTHROPIC_API_KEY` in its environment, so a scan sends no file to an LLM provider.
- **The bundled scanner runs with onnxruntime's telemetry off ([#218](https://github.com/opena2a-org/ai-trust/issues/218)).** The scanner's deep scan loads `onnxruntime-node`, and `onnxruntime-node` 1.30.0, loaded on macOS with `HOME` set to an empty directory, created `deviceid`, `onnxruntime.db`, `onnxruntime.db-shm` and `onnxruntime.db-wal` in `Library/Application Support/Microsoft/DeveloperTools/.onnxruntime` under it; with `ORT_DISABLE_TELEMETRY` set to `1` it created none of them. ai-trust now sets `ORT_DISABLE_TELEMETRY=1` for the scan and for the `--version` check, beside `OPENA2A_TELEMETRY=off`, and the [contribution guide](docs/use-cases/contribute-scans.md) names it.
- **The `ai-trust check` command in the not-found Next Steps quotes a name with shell syntax in it ([#218](https://github.com/opena2a-org/ai-trust/issues/218)).** `check 'shell-lib; echo injected' --no-scan` printed `→ Scan locally  ai-trust check shell-lib; echo injected`, and with `--json` the first `nextSteps` entry was the same unquoted command, so a copy-paste ran `echo injected`. Both now print `ai-trust check 'shell-lib; echo injected'`, with the same quoting as the registry-answer Next Steps; a name made only of ASCII letters, digits and `_@%+=:,./-` is printed as it is.
- **The `hackmyagent check` command that `check` suggests quotes a registry name with shell syntax in it ([#141](https://github.com/opena2a-org/ai-trust/issues/141)).** For a package the registry classifies as a library, `check --no-scan` printed the name from the registry's answer as it came, so an answer naming `shell-lib; echo injected` for `check pip:shell-lib` printed two commands on one line. A name with any character other than ASCII letters, digits and `_@%+=:,./-` is now single-quoted (`hackmyagent check 'pip:shell-lib; echo injected'`), in the text output and in the `--json` `nextSteps`, and so is the name in the `ai-trust check` command in the Next Steps of a registry answer. A name made only of those characters is printed as it is (`hackmyagent check pip:requests`).
- **A saved contribution `enabled` value other than the boolean `true` is not consent ([#141](https://github.com/opena2a-org/ai-trust/issues/141)).** With `{"contribute":{"enabled":"false"}}` in `~/.opena2a/config.json`, `ai-trust config contribute status --json` printed `{"contribute": true}`; `check` and `audit` decide whether to share a scan from the same reading. A value that is not `true` or `false` is now read as not set: `status --json` prints `{"contribute": null}` for that file, and it does not count as consent to share.
- **The bundled scanner's classification telemetry does not take a saved contribution value that ai-trust reads as not set as consent ([#147](https://github.com/opena2a-org/ai-trust/issues/147)).** With `{"contribute":{"enabled":"false"}}` in `~/.opena2a/config.json` and `OPENA2A_HOME` unset, the pinned `hackmyagent` 0.33.2 reads the choice through `@opena2a/shared`, whose `isContributeEnabled()` returns the saved string `"false"`, and its NanoMind classification telemetry is gated on that value being truthy: in that environment the scanner queued a classification stat for a classified file. When the saved value is truthy but not the boolean `true` (tested with `"false"`, `"true"` and `1`), `OPENA2A_HOME` is unset and `~/.hackmyagent/config.json` does not hold `"contribute": true`, ai-trust now runs the scanner with `OPENA2A_HOME` set to `~/.opena2a`; the scanner then reads that file itself and takes only the boolean `true` as consent. With `"false"` saved, a classified file now queues no classification stat; with `true` saved, it still queues one. For a saved `true`, `false`, `0` or `null`, for no config file, and when `OPENA2A_HOME` is already set, the scan runs without an added `OPENA2A_HOME`. While `~/.hackmyagent/config.json` holds `"contribute": true`, the scan runs as the entry for [#150](https://github.com/opena2a-org/ai-trust/issues/150) describes.
- **The bundled scanner's classification telemetry does not take a saved contribution value that ai-trust reads as not set as consent while the scanner's legacy config holds an opt-in ([#150](https://github.com/opena2a-org/ai-trust/issues/150)).** With `{"contribute":{"enabled":"false"}}` in `~/.opena2a/config.json` and `{"contribute":true}` in `~/.hackmyagent/config.json`, `config contribute status --json` prints `{"contribute": null}`, yet `check <name> --scan-path <dir> --json` on a directory holding one source file attempted a `POST` to `https://api.oa2a.org/api/v1/nanomind/telemetry`. ai-trust ran the scanner without `OPENA2A_HOME` in that case, because with `OPENA2A_HOME` at `~/.opena2a` a `secure` run moves that legacy opt-in into `~/.opena2a/config.json` as `true`; without it, the pinned `hackmyagent` 0.33.2 read the saved `"false"` as consent. When the saved value is truthy but not the boolean `true` (tested with `"false"`, `"true"` and `1`), `OPENA2A_HOME` is unset and the legacy file holds `"contribute": true`, the scan now runs with `OPENA2A_HOME` set to `opena2a` under the null device (`/dev/null/opena2a` on macOS). The scanner reads no saved choice there and cannot write one: it queues no classification stat for a classified file, before or after its move of the legacy opt-in, and that move stops before it changes either file. Measured on macOS with the files above: the same `check` attempted no request to `/api/v1/nanomind/telemetry` and left both files as they were, where with `OPENA2A_HOME` unset the scanner had also added its default fields and a scan count to `~/.opena2a/config.json`; a deep `secure` run of the pinned scanner on that directory gave the same JSON report, apart from its time fields, as with `OPENA2A_HOME` unset. A saved boolean `true` still runs the scan without an added `OPENA2A_HOME`.
- **The bundled scanner runs with your saved choices out of its reach and its own telemetry off, and ai-trust passes it every decision by flag ([#147](https://github.com/opena2a-org/ai-trust/issues/147)).** This replaces the `OPENA2A_HOME` handling in the two entries above. The pinned `hackmyagent` 0.33.2 reads the saved contribution choice from `~/.opena2a/config.json` (or `$OPENA2A_HOME/config.json`), moves a `"contribute": true` from its legacy `~/.hackmyagent/config.json` into that file, saves its scan count there, and sends its NanoMind classification telemetry and a usage event when the saved choices read as on; `--no-contribute` changes none of that. ai-trust now runs it, for the scan and for the `--version` check, with `HOME`, `USERPROFILE`, `OPENA2A_HOME` and `XDG_CONFIG_HOME` set to a new temporary directory that is removed after the run, and with `OPENA2A_TELEMETRY=off`; it still passes `--no-contribute`, `--deep` or `--static-only`, and `--analm`. The directories a deep scan reads its classifier models from, `~/.nanomind` and `~/.opena2a/nanomind`, are linked into that directory, so the scan finds its models where it did and a model it downloads still lands in `~/.nanomind/models`; ai-trust creates `~/.nanomind` first when it is missing, as the scanner did on every run. A new end-to-end test runs `check --scan-path` and `audit --scan-missing` with the real scanner in a temporary home over every combination of the `~/.opena2a/config.json` value (absent, `true`, `false`, `"true"`, `"false"`, not valid JSON), `~/.hackmyagent/config.json` (absent, `"contribute": true`, `"contribute": false`), `--contribute`, `--no-contribute` or neither, and `--no-deep` or not: 216 runs, with the scanner process's requests sent to a local capture server except for the two kinds named below. Before this change all 216 failed. In every run the scanner opened the legacy file and sent a usage event. In the 192 runs other than the 24 with `"true"` or `"false"` saved together with the legacy opt-in, which ran with `OPENA2A_HOME` under the null device, it also opened and rewrote `~/.opena2a/config.json` (creating it when it was absent, and replacing a file that was not valid JSON with the shared defaults). In the 36 runs with `"contribute": true` in the legacy file and `~/.opena2a/config.json` absent, `false` or not valid JSON, it saved contribution as on in `~/.opena2a/config.json` and removed the opt-in from the legacy file. In the 18 default (deep) runs with `true` saved, it posted classification telemetry to `api.oa2a.org`, with or without `--no-contribute`. Now, in all 216, the scanner opens neither file, the legacy file stays byte-identical, `~/.opena2a/config.json` does too except for the scan count ai-trust itself saves there when an audit shares its scans, as before, and no request from the scanner reaches the capture server. The test does not send two kinds of request there: the classifier model download a deep scan makes when no model is installed, which a local stub answers with a 404, and loopback requests to ports other than the stub's and the capture server's, which go through unchanged and which a deep scan makes to the NanoMind daemon at `127.0.0.1:47200`. The JSON of `check --scan-path --json` is byte-identical before and after on three fixtures, deep and with `--no-deep`. `--help` and the contribution guide no longer say that `--no-contribute` leaves the scanner's classification telemetry running, the exception the `--no-contribute` entry below describes.
- **`audit --scan-missing` downloads the names in your dependency file, not the names the registry answers with ([#137](https://github.com/opena2a-org/ai-trust/issues/137)).** The scan downloaded each not-found answer's `name`, with `npm pack` for a `package.json`. Against a registry whose not-found answer named a `git+file://` repository instead of the dependency `package.json` listed, `audit package.json --scan-missing` printed `Scanning git+file://...`, and npm ran that repository's `prepare` script before the identity check refused the tarball. Now each answer is matched to an entry of the dependency file (ignoring case for npm, after PEP 503 normalization for PyPI) and the file's spelling is downloaded, scanned and, with consent, sent in the scan ping and contribution. An answer that matches no entry prints `Not scanning <name>: the registry answered with a name the dependency file does not list.` and nothing is downloaded; in the same run the `prepare` script did not run and the exit code stayed 2. The npm download, which `check` also uses, refuses a name that is not an npm registry package name (an optional `@scope/`, then letters, digits, `.`, `_` and `-`, with no `.tgz`, `.tar` or `.tar.gz` ending) before npm runs, so `check git+file://<repo>` exits 1 with `is not a valid npm package name`, and it runs `npm pack --ignore-scripts`.
- **Scanning a PyPI package no longer runs the package's build script, and no longer needs `pip` ([#123](https://github.com/opena2a-org/ai-trust/issues/123)).** `audit requirements.txt --scan-missing` downloaded each package the registry does not have with `pip download --no-deps --no-binary :all:`, and pip prepares a source archive's metadata by running its build backend: with pip 26.0, `pip download` of a local source archive whose `setup.py` writes a file printed "Preparing metadata" and the file existed. ai-trust now reads the latest release from the PyPI JSON API (`https://pypi.org/pypi/<name>/json`), downloads the source archive listed there (or a wheel when the release has none, a pure-Python wheel first), refuses the file unless its SHA-256 matches the digest PyPI lists for it, and extracts it with `tar` or `unzip`. Nothing in the package runs, and `check pip:<name>` uses the same download. Because pip is not used, a machine with only `pip3` on its PATH, where the scan failed with `spawn pip ENOENT`, now scans PyPI packages; the download goes to pypi.org directly and does not use pip's index or proxy settings. A name that is not a valid PyPI project name is refused before any request.
- **A dependency name that looks like an option, and a symlinked manifest in a downloaded package, are no longer acted on ([#123](https://github.com/opena2a-org/ai-trust/issues/123)).** `audit` passed each `package.json` dependency name to `npm pack` as a bare argument, so a dependency named `--version` made npm print its version instead of downloading a package. The name now follows `--`, so npm no longer reads it as an option. Reading the downloaded package's version (`PKG-INFO`, `*.dist-info/METADATA`, `package.json`) skips a manifest or `.dist-info` directory that is a symlink, and the npm identity check refuses a `package.json` that is not a regular file, so neither reads a file outside the extracted package.
- **The build-tree lockfile is refreshed to patched releases, clearing every advisory `npm audit` reports for it, with no manifest change and an empty acceptance list.** `npm audit --package-lock-only` on the committed lockfile reported 11 vulnerabilities (1 critical, 5 high, 5 moderate), all of them published, or revised to cover the locked version, after the last refresh (whose own audit found 0 vulnerabilities), and all with a patched release inside the declared ranges: `proxy-addr` (critical), `@modelcontextprotocol/sdk`, `adm-zip`, `fast-uri`, `js-yaml`, `source-map-js` (high), and `hono`, `ip-address`, `qs`, `vitest`/`@vitest/mocker` (moderate). `npm audit fix --package-lock-only` moves 55 packages forward, removes 7 (`@emnapi/*`, `@napi-rs/wasm-runtime`, `@rolldown/binding-wasm32-wasi`, `@tybys/wasm-util`, `tslib`) and adds 1 (`@rolldown/binding-android-arm-eabi`), every `resolved` on `registry.npmjs.org`, no downgrade. `package.json` was untouched: `hackmyagent` stayed pinned `0.25.0` (the pin moved to `0.33.2` later in this release), lockfiles are not published, and the refresh by itself changed no published file. Nothing was accepted: `ACCEPTED_ADVISORIES` stays empty, and both the build-tree gate and the consumer-resolution gate measure 0 advisories on this tree.
- **The last accepted advisory is retired by remediation, not by re-dating it, and the acceptance list is now empty.** `GHSA-xcpc-8h2w-3j85` (adm-zip <0.6.0) was accepted for the shipped artifact because `onnxruntime-node` pinned adm-zip inside a caret on 0.5.x while the patched release was 0.6.0, so nothing in this repo could reach it. That is no longer true: `onnxruntime-node@1.29.0` is the current stable and declares `adm-zip: ^0.6.0`, and `hackmyagent@0.25.0`, the pin at the time, admits it via `onnxruntime-node: ^1.24.3`. A fresh consumer install therefore already resolved clean while this repo's **committed lockfile** still pinned `onnxruntime-node@1.27.0 -> adm-zip@0.5.18` — so the consumer gate began failing on a stale allowlist entry. That failure was the gate working: the entry's own text pre-registered this exit ("when the answer becomes yes, that derivation fails and the remedy is to raise the resolution, not to re-date this"), and the gate refused to let a lockfile that no longer matched reality stand.
  The remedy is `npm audit fix --package-lock-only`, which moves exactly three packages — `adm-zip 0.5.18 -> 0.6.0`, `onnxruntime-node 1.27.0 -> 1.29.0`, `onnxruntime-common 1.27.0 -> 1.29.0`, every `resolved` on `registry.npmjs.org` — plus deleting the acceptance entry and its now-unreachable `derive`. **No manifest change**: `hackmyagent` stayed pinned `0.25.0` (the pin moved to `0.33.2` later in this release), lockfiles are not published, so the remedy by itself changed no published file and was not a release. The two edits are atomic and were proven so: with the refreshed lockfile but the entry still listed, the build-tree gate passes; with the entry deleted but the old lockfile, it fails with "Unlisted high advisory in the build tree". Neither ships alone.
  `ACCEPTED_ADVISORIES` is now empty, which is the healthy steady state rather than dead code — the shared list and its one-way coupling stay exactly as they were, so a future advisory in either tree still fails, a waiver that stops matching still fails as stale, and an expired date still fails. The note below stating this advisory "cannot be fixed in this repo at all" was true when written, when 1.27.0 was the latest stable; it is left in place as history rather than edited, because a changelog records what was believed at the time.
  Not resolved by this, and tracked separately: the unsigned, unchecksummed native-binary fetch in `onnxruntime-node`'s postinstall, which is a strictly stronger problem than the advisory it carried.

- **The release workflow no longer runs third-party install scripts in the job that holds the npm publish identity — and no longer runs them at all.** `release.yml` declared `contents: write` + `id-token: write` at workflow level; the `release` job declared no override, so it inherited both while running `npm ci` — which executes every dependency's install script, including `onnxruntime-node`'s, which downloads a nupkg from `api.nuget.org` and extracts a native `.so` with no signature or checksum check — and then ran `npm publish --provenance` in that same job. Any compromised transitive dependency therefore had code execution alongside the OIDC credential that mints our provenance attestations. Now: the workflow grants nothing (`permissions: {}`) and every job declares its own block, so no job inherits; `build` compiles and tests with **`npm ci --ignore-scripts`** and holds no `id-token`; `publish` holds `id-token: write` and nothing else, does no checkout and no `npm ci`, and publishes the tarball `build` already packed and checksummed (`npm publish <tarball>` fires no lifecycle hooks — every one is gated on `spec.type === 'directory'` in the npm CLI, verified against 11.19.0 source and measured, 0 of 4 hooks fired on a probe); `github-release` is separate so no job holds both the publish identity and repo write. Skipping install scripts was measured, not assumed — build clean, 258 tests pass, `release-smoke:corpus` 9/0 — and cannot change the artifact, since `files` is `["dist","README.md"]` and `dist` is `tsc` output. **The honest limit, because this should not be read as more than it is:** the SLSA predicate records workflow, repo, commit and run — never which *job* produced the bytes — so provenance granularity is the run, not the job. What this removes is OIDC-token exfiltration and attestation-minting over arbitrary content; combined with `--ignore-scripts` it also removes the code execution that could have poisoned `dist/` before packing, which is the content-integrity half.
- **The provenance verification gate could never fail, and has now been made able to.** The step polled `npm view <pkg> dist.attestations --json 2>&1` and treated any non-empty, non-`null`, non-`{}` result as success — but `2>&1` captures stderr, and an `E404` (exactly what registry propagation lag returns, which is the entire reason for the five-minute poll) is a ~740-character non-empty string. Measured against the live registry: the old logic reports "Provenance verified" and exits 0 on the first iteration for a version that does not exist. It now captures stdout only and asserts the shape (`.provenance.predicateType == "https://slsa.dev/provenance/v1"`), proven both ways — it rejects the E404 case and still passes against a genuinely provenanced published version.
- **Three further release-path defects fixed while in there.** Values crossing from the build job into the publish job are passed via `env:` and validated rather than interpolated into `run:` bodies — GitHub expands `${{ }}` into the script text before bash parses it, so a crafted tarball filename (writable by the very install scripts this change is defending against) would have executed as code in the hardened job, handing back the whole attack. `npm publish` now passes `--registry` explicitly, because `publishConfig` inside the tarball's own manifest is flattened into the publish options and `registry` is not otherwise a CLI flag, so a poisoned manifest could redirect the publish. And the publish is now idempotent (skips when the version is already on npm), so a green publish followed by a red verification no longer leaves a re-run permanently stuck and the GitHub release never created. Also added: a tag-vs-manifest-version assert in `build` (failing free, before the irreversible step), and an npm-version floor assert in `publish`, which no longer runs `npm ci` and so cannot assume a recent npm.
- **The build-tree advisory gate is honestly green instead of permanently red, and it measures a set difference rather than a count.** `npm audit --package-lock-only` on the committed lockfile reported 12 vulnerabilities / 8 high. A real `npm audit fix --package-lock-only` (not `--dry-run`, which reports no change against this tree and is a false negative) clears 10 of them with **zero waivers, zero `overrides`, and no manifest change**: `fast-uri`, `hono`, `ip-address`, `js-yaml`, `nanoid`, `postcss`, `@hono/node-server`, `@modelcontextprotocol/sdk`, `body-parser`, plus `global-agent` 3.0.0 → 4.1.3. The `esbuild` low advisory is cleared **forward** rather than by the downgrade `npm audit fix` proposes: `npm audit fix` moves esbuild 0.27.7 → 0.27.2 (backwards, out the bottom of the advisory range) because it minimises movement, whereas updating `tsx` 4.21.0 → 4.23.12 — already admitted by the declared `^4.21.0` — brings a `~0.28.0` range and resolves esbuild 0.28.2, clear of the advisory. A downgrade buried in a 45-version refresh is a supply-chain shape we would flag as a finding in someone else's repo. What remains is exactly one advisory (`GHSA-xcpc-8h2w-3j85`, adm-zip <0.6.0, counted twice because `onnxruntime-node` is flagged for depending on it), which cannot be fixed in this repo at all: `onnxruntime-node` pins `adm-zip` inside a caret on 0.5.x and the patched release is 0.6.0. It was already formally accepted for the **shipped** artifact with a dated, self-invalidating, derive-backed waiver — so the gate now asserts "high/critical advisory ids, minus the ids already accepted for the shipped artifact, is empty" instead of "the count is zero". **The severity threshold is unchanged, and no suppression primitive was added** — no lowered `--audit-level`, no `|| true`, no `continue-on-error`. A new high advisory fails on the run it appears; both enforcement rules were proven able to fail on purpose before shipping. Acceptances now live in one place, `scripts/lib/accepted-advisories.mjs`, read by both the build-tree and consumer gates, and the coupling is one-way by construction: an advisory can be waived in the build tree only because it is already accepted for users, never the reverse. The job is renamed `audit` → `build-tree-audit` for the artifact it measures, and restored to the weekly schedule it had been excluded from *because* it was permanently red.
- **Control characters in a registry answer are removed before text output ([#129](https://github.com/opena2a-org/ai-trust/issues/129)).** A registry answer is remote data, and its strings were printed as received. In `check <package> --no-scan`, a `knownCves` entry carrying an OSC escape sequence and a CR LF was written to the terminal byte for byte, and the text after the line break appeared as an output line of its own. Text output now replaces a run of tabs and line breaks with one space and removes the other C0 controls (ESC and BEL among them), DEL and the C1 controls, so that entry prints as `CVE-]0;x-1 EXTRA LINE` on the `CVEs` line. The filter is applied to the registry's strings in the `check --no-scan` block, in the table and summary of `batch` and `audit`, in the `Scanning ...` and `Could not scan ...` lines of `audit --scan-missing`, in the out-of-scope notice for a registry-classified library, in the `check mcp:<name>` narrative block, and in the registry error message that `check`, `batch` and `audit` print, which quotes the start of a response body that is not JSON. A listed advisory identifier longer than 40 characters is cut to 40, ending in `...`. `check --json` carries each string as the registry sent it; DEL and the C1 controls, which `JSON.stringify` leaves raw, are written there as `\u00XX` escapes.
- **Rejected, and recorded so it is not retried:** the root-manifest `"overrides": { "adm-zip": "0.6.0" }` used to fix the identical advisory in the `opena2a` monorepo does **not** transfer here, and the difference is not cosmetic. That repo's root manifest is `private: true` and never published; ai-trust's root manifest **is** the published artifact. Verified by packing a probe and extracting the tarball: an `overrides` block is carried verbatim into the published `package.json`, where npm ignores it (overrides are honoured only in a consuming project's own root) — so it would ship, to every user, a manifest asserting we pin adm-zip to the patched version while their install resolves the vulnerable one. A false claim in a published manifest, from a tool whose job is inspecting other people's manifests.

### Changed

- **The out-of-scope notice of `check` is printed on stdout ([#218](https://github.com/opena2a-org/ai-trust/issues/218)).** `check express --no-scan > out.txt` left `out.txt` empty and printed the notice (`express  library (by name — no registry data)`, the `Out of scope for ai-trust` line and the `npx hackmyagent check express` command) on stderr, while the same command with `--json` printed on stdout. Both notices, for a library the registry classifies and for one recognized by name, now go to stdout, as the registry answer and the not-found block do; the exit code is unchanged.
